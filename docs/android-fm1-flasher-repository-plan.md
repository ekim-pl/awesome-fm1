# Signed firmware repositories in FM-1 Flasher

Implement this plan in `android-fm1-flasher` after a signed Awesome FM-1 endpoint and its fingerprint are available. Use [the repository protocol](firmware-repository.md#signed-entry-wire-format) and [JSON schema](../schema/repository.schema.json) as the contract. The Pages entry path is `/awesome-fm1/repo/v1/entry.json`. Keep the current catalog URL available to released app builds.

## 1. Verify and decode a signed snapshot

- Add a `SIGNED_REPOSITORY` provider to `CatalogProviderType` and the Android registry in `app/.../CatalogProvider.kt`. Start with an opt-in custom source in Settings → Firmware sources. Reuse its HTTPS transport, URL scopes, credential store, refresh policy and error UI.
- Take the URL and SHA-256 key fingerprint from the user or an authenticated bundled preset. Store the local source ID independently of the signed `repository.id`. Bind the repository ID on first verified refresh. Allow two publishers with the same declared ID to coexist as separate subscriptions. A custom-source key change requires explicit re-enrollment with a new independently confirmed fingerprint. Plan a bundled app update for built-in key replacement.
- Use the platform Ed25519 verifier against the decoded DER SubjectPublicKeyInfo. Check the fingerprint, envelope format, encoding and byte limits before verification. Verify the signature over the decoded payload bytes and parse the payload only after success. The envelope has one potentially large Base64 string, so it needs its own structural limits. The legacy `JsonLimits` string cap applies to index fields, with bounded depth, count and byte size for the decoded index. Reject duplicate keys, unknown schema versions, invalid IDs and URLs, invalid UTC dates and broken recommendation references as failures of the entire snapshot.
- Track the highest accepted sequence and the SHA-256 of its signed payload. Reject a lower sequence or different payload at the same sequence. An identical payload may be revalidated while unexpired. Inject the clock into decoding so expiry, clock skew and HTTP 304 behavior are testable. A 304 can extend ordinary cache freshness only when it refers to an accepted, unexpired snapshot. Force an unconditional check when the saved signed snapshot expires.
- Extend `CatalogSnapshot`, `CatalogSource` serialization in `CatalogDatabase` and `commitSnapshot` to persist the key pin, sequence, digest, expiry and withdrawal state atomically with entries. Reuse the source revision check so an in-flight refresh cannot commit across a configuration change. Signature, pin or replay failure keeps the last accepted snapshot visible and blocks new downloads from the failed source until a valid refresh.

## 2. Map projects into the current library

- Add one row per project using the recommended artifact. Keep the row key `sourceId/project.id`. Use the version and beta flag from the release and the hash, product and legacy chip label from the artifact. Map name, author, summary, links, artwork, categories and date through the existing display fields. A project without an available recommendation can be displayed as non-downloadable once the UI has an explicit browse-only model. Do not create placeholder hashes in `CatalogEntry`.
- For GitHub releases, use the reviewed repository, tag and numeric asset ID through the existing release resolution path. Verify that the resolved asset URL matches the signed reference, use only the existing approved GitHub redirects, then verify size, hash, product and package structure. For direct downloads, require the existing approved package URL scope before requesting bytes. Keep authentication tied to its configured origin. Apply the same path and origin checks to artwork separately.
- Keep recommendation changes separate from withdrawals. A superseded mutable URL blocks a new download of that artifact. A locally saved, verified old package still follows existing offline policy. An explicit signed withdrawal blocks matching `sourceId/project.id/sha256` downloads and installations, including downloaded packages and queued tasks, as soon as that withdrawal is known. Check the withdrawal again before device writes. Feed known withdrawals into the current removal, conflict and package validation checks. Preserve the pinned stock recovery exception as an app decision.
- Keep the recommended-only projection for the first app release. Preserve favorites, source filters, sorting, updates by changed hash, local library access and task assignments. Treat the full history as a later UI step. Android already stores download rows by source, project and hash. Audit lookup, pruning and task selection before exposing a version picker, since current UI lookups still center on the project key.

## 3. Roll out the built-in source

1. Test one custom signed source against a local test server and a public staging feed. Use the Python signer to generate fixtures with a disposable test key. Cover a valid snapshot, tampering, wrong key, expiry, rollback, equal sequence with different bytes, expired 304, unsupported format, invalid references and source reconfiguration during refresh.
2. Test an upgrade from a device with Awesome FM-1 enabled, favorites, a saved package and a queued assignment. Preserve `awesome-fm1` as the local ID and reset conditional request state on provider change. Keep the built-in source disabled by default for new installs. Switch it only after the target endpoint and pinned key ship together. Retain authenticated custom JSON, raw GitHub-release and package URL providers, including the Hub's 24-hour refresh rule.
3. Add integration cases for an ordinary update, withdrawn old hash versus the current hash, offline launch, blocked redirects, mutable URL changes, conflicting metadata across sources and legacy stock recovery. Run Android unit and instrumentation tests and confirm a signed-source refresh leaves the existing device queue and offline flows usable.
4. Implement shared-client support separately. `shared/.../FirmwareRepository.kt` uses a legacy Hub-oriented codec and storage model. Share the wire fixtures and pure decoder where practical. Validate Ed25519 support and source/storage parity on each target before enabling signed sources there.
